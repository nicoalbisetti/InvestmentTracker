1. RESUMEN DE LA FUNCIONALIDAD
=============================================================================

Reemplazar el cálculo de retornos por período (return_1m, return_3m,
return_6m, return_12m) en el endpoint POST /api/positions/recalculate-stats
por una lógica que no dependa de campos legacy del Excel (gain_pct,
applications, redemptions, previous_balance, calculated_balance).

El nuevo cálculo usa exclusivamente los campos que los importers modernos
sí escriben: balance_brl, unit_price, quantity.

La fórmula varía según el tipo de instrumento:

  - accion / fii:
      Retorno de precio puro: (unit_price_actual - unit_price_N_meses_atrás)
                              / unit_price_N_meses_atrás
      Esto mide el rendimiento del activo sin considerar compras/ventas.

  - renta_fija / fundo / previdencia / saving / fgts / outro / exterior:
      Variación de balance ajustada por flujos estimados.
      Ver sección 3 para la lógica exacta.

Adicionalmente, equity_recalculate.py debe empezar a calcular y persistir
gain y gain_pct en MonthlyPosition al recalcular posiciones de acciones/FIIs,
para que en el futuro el cálculo de retornos pueda encadenar esos valores.

3. LÓGICA DE CÁLCULO POR TIPO — compute_period_return()
=============================================================================

Crear la función helper compute_period_return() dentro de
backend/app/routers/positions.py (o en un módulo nuevo
backend/app/services/return_calculator.py si resulta más limpio).

Firma:
  def compute_period_return(
      instrument_id: int,
      instrument_type: str,
      latest_date: date,
      n_months: int,
      db: Session,
  ) -> Optional[float]:

Comportamiento según tipo:

--- 3.1 Tipos: accion, fii ---

  Objetivo: retorno de precio puro, sin interferencia de compras/ventas.

  1. Obtener mp_actual: el MonthlyPosition del instrumento con
     date == latest_date.
     Si mp_actual.unit_price es None → retornar None.

  2. Calcular target_date = latest_date - relativedelta(months=n_months).

  3. Obtener mp_prev: el MonthlyPosition del instrumento con
     date <= target_date, balance_brl > 0, unit_price IS NOT NULL,
     ORDER BY date DESC, LIMIT 1.
     Si no existe → retornar None.

  4. Si la diferencia entre mp_prev.date y target_date es mayor a
     45 días → retornar None (el período real difiere demasiado del nominal).

  5. Retornar (mp_actual.unit_price - mp_prev.unit_price) / mp_prev.unit_price

  NOTA: No usar balance_brl para acciones/FIIs porque ese campo incluye
  el efecto de compras y ventas (balance = quantity × unit_price).


--- 3.2 Tipos: renta_fija, fundo, previdencia, saving, fgts, outro, exterior ---

  Objetivo: aproximar el retorno del activo excluyendo flujos de capital.
  Para renta fija sin rescates parciales esto es exacto. Para fondos con
  movimientos frecuentes es una aproximación.

  Estrategia: Modified Dietz simplificado usando solo balance_brl.
  Asumimos que si no hay campos de flujo disponibles (legacy vacíos),
  el único escenario donde la variación de balance ≠ retorno es cuando
  hay una aplicación o rescate registrada en Transaction.

  1. Obtener mp_actual con date == latest_date.
     Si mp_actual.balance_brl is None o <= 0 → retornar None.

  2. Calcular target_date = latest_date - relativedelta(months=n_months).

  3. Obtener mp_prev: date <= target_date, balance_brl > 0,
     ORDER BY date DESC, LIMIT 1.
     Si no existe → retornar None.

  4. Si la diferencia entre mp_prev.date y target_date es mayor a
     45 días → retornar None.

  5. Consultar flujos netos del período desde la tabla transactions:
       net_flow = SUM(amount_brl) WHERE
         instrument_id = instrument_id
         AND date > mp_prev.date
         AND date <= latest_date
         AND type IN ('aplicacion', 'rescate')
       Para 'aplicacion': sumar positivo.
       Para 'rescate': sumar negativo.

     Si no hay registros en transactions para este instrumento → net_flow = 0.

  6. Calcular base ajustada:
       adjusted_base = mp_prev.balance_brl + (net_flow * 0.5)
     Si adjusted_base <= 0 → retornar None.

  7. Retornar:
       (mp_actual.balance_brl - mp_prev.balance_brl - net_flow) / adjusted_base


--- 3.3 Período de N meses: criterio de gap máximo ---

El criterio de 45 días del punto 4 en ambas ramas aplica así:

  allowed_gap = 45  # días
  actual_gap = abs((mp_prev.date - target_date).days)
  if actual_gap > allowed_gap:
      return None

Esto evita que un instrumento con dato de hace 8 meses aparezca con un
return_3m calculado silenciosamente sobre 8 meses.

Nota: para períodos de 12 meses el gap máximo puede ser hasta 45 días,
lo que cubre meses que llegan tarde por el ciclo de importación.

4. PERSISTENCIA DE gain / gain_pct EN equity_recalculate.py
=============================================================================

Modificar backend/app/services/equity_recalculate.py en la función
recalculate_equity_positions() para calcular y persistir gain y gain_pct
en cada MonthlyPosition que procesa.

Lógica a agregar dentro del loop por mes, DESPUÉS de actualizar
mp.quantity, mp.avg_price y mp.balance_brl:

  # Calcular gain mensual y gain_pct
  prev_mp = MonthlyPosition con
    instrument_id == instrument_id
    AND date == mp.date - relativedelta(months=1)
    (puede ser None si es el primer mes)

  if prev_mp and prev_mp.balance_brl and prev_mp.balance_brl > 0:
      # Flujos de trades del mes (compras son salidas de caja, ventas entradas)
      trades_this_month = lista de trades ya computada en el loop
      net_trade_flow = sum(
          t.quantity * t.price if t.trade_type == "compra" else -(t.quantity * t.price)
          for t in trades_this_month
      )
      # gain = variación de balance descontando el flujo neto de trades
      mp.gain = (mp.balance_brl or 0) - (prev_mp.balance_brl or 0) - net_trade_flow
      adjusted_base = (prev_mp.balance_brl or 0) + net_trade_flow * 0.5
      if adjusted_base > 0:
          mp.gain_pct = mp.gain / adjusted_base
      else:
          mp.gain_pct = None
  else:
      mp.gain = None
      mp.gain_pct = None

IMPORTANTE: Este cambio hace que gain y gain_pct empiecen a ser válidos
para acciones/FIIs a partir de la próxima importación o recalculo.
Los datos históricos anteriores a este cambio seguirán con gain=None,
lo cual es correcto (mejor null que un número incorrecto).

8. CASOS BORDE Y VALIDACIONES
=============================================================================

--- 8.1 Instrumento sin unit_price en ningún mes (accion/fii reciente) ---
  compute_period_return devuelve None para todos los períodos.
  return_source = "none".
  Las celdas muestran "—". Correcto — es mejor null que inventar un número.

--- 8.2 Renta fija sin movimientos en Transaction ---
  net_flow = 0. El cálculo se reduce a:
    (balance_actual - balance_anterior) / balance_anterior
  Que para renta fija sin rescates parciales es el retorno real.

--- 8.3 Instrumento con rescate total en el período ---
  mp_actual.balance_brl = 0 o instrument.status = "cerrado".
  El instrumento no aparece en el query de recalculate-stats
  (ya filtra balance > 0). No afecta el cálculo.

--- 8.4 Instrumento nuevo (menos de N meses de historia) ---
  mp_prev no existe para períodos largos → None para esos períodos.
  Por ejemplo: un instrumento de 2 meses tiene return_1m pero no
  return_3m, return_6m ni return_12m. Correcto.

--- 8.5 Instrumento con gap > 45 días ---
  Devuelve None explícitamente en lugar de silenciosamente calcular
  sobre un período diferente al nominal. La UI muestra "—".

--- 8.6 XP International (USD) ---
  Los instrumentos de XP International tienen unit_price en USD y
  balance_brl calculado con usd_rate.
  Para tipo "accion" (ETFs) → se usa la rama unit_price.
  El retorno resultante es en USD (variación de precio en USD).
  NOTA: Esto es consistente porque unit_price para XP Intl está en USD.
  Dejar así por ahora. Una conversión a BRL requeriría usd_rate histórico
  mes a mes, lo cual es una mejora futura.

--- 8.7 Instrumentos con custodian_override (cross-custodio) ---
  Pueden existir dos MonthlyPosition para el mismo instrumento en el
  mismo mes (mismo instrument_id, distinto custodian_override).
  Para el cálculo de retorno: usar la suma de ambas para balance, o
  si es por unit_price usar cualquiera (el precio es el mismo).

  Simplificación aceptable: la query de recalculate-stats ya agrupa
  por instrument_id via _latest_positions_subquery. No se necesita
  cambio aquí — el retorno se calcula al nivel del instrument, no
  del MonthlyPosition individual.

10. CRITERIOS DE ACEPTACIÓN
=============================================================================

1. POST /api/positions/recalculate-stats completa sin errores con la BD
   actual.

2. Para instrumentos de tipo accion/fii con unit_price disponible:
   return_1m != None Y return_source == "price".

3. Para acciones/FIIs con unit_price disponible solo en el mes actual pero
   no N meses atrás: return_Nm == None para ese período específico.

4. Para instrumentos de renta_fija con >= 2 meses de historia:
   return_1m != None Y return_source == "balance".

5. Para un instrumento de renta fija que tuvo una Transaction de tipo
   "aplicacion" en el período: el return calculado es diferente al que
   se obtendría sin ajustar por net_flow (verificar manualmente con un
   ejemplo concreto en la BD).

6. Para un instrumento nuevo con 1 mes de historia:
   return_1m != None, return_3m == None, return_6m == None,
   return_12m == None.

7. En Positions.tsx, al hacer hover sobre una celda de retorno de una
   acción, se muestra el tooltip "Retorno calculado sobre precio unitario
   (excluye compras/ventas)".

8. En Positions.tsx, al hacer hover sobre una celda de retorno de renta
   fija, se muestra el tooltip sobre método de balance.

9. equity_recalculate: después de crear/editar un EquityTrade, las
   MonthlyPosition afectadas tienen gain y gain_pct != None (si hay mes
   anterior disponible).

10. No hay regresiones en los otros endpoints de /api/positions.
